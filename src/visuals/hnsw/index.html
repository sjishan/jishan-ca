Why doesn't HNSW have to check every vector?

A vector database can always find the stored vector nearest to your query by measuring every vector, but that makes the work grow with the index. Run the comparison below and watch HNSW use sparse upper layers to get close first, then return the same answer after 46 distance checks in this 1,500-vector example.

In that run HNSW measured 46 of the 1,500 vectors and returned the same nearest vector as the full scan. The next five steps show why that can happen, and the sixth lets you change the settings yourself.

Step 1 / 6

Every answer costs a full scan

A vector database stores vectors, i.e. lists of numbers produced by a model from text, images, or other data. You can treat each vector as a point in space. When you give the database a new query vector, the job is to find the stored vector closest to it. That stored vector is the nearest neighbor.

The most direct method always returns the right answer. Measure the distance from your query to every stored vector and keep the smallest distance. Each measurement is one distance check, i.e. what the papers call a distance computation. That is the unit of cost used throughout this page.

With 500 stored vectors, a full scan costs exactly 500 distance checks.

Drag the query anywhere on the map, then press Check every vector. The counter will climb to 500 because every stored vector has to be measured.

Step 2 / 6

Link the vectors together, then search by moving between them

Now join each vector to its four nearest vectors. Those connections turn the points into a graph. Each point is a node, each connection is a link, and the nodes connected to one node are its neighbors.

Once the vectors are linked, you can search by moving through the graph instead of measuring every vector. The search begins from the same fixed node each time, called the entry point. In this figure, the entry point sits in the bottom left corner.

The search follows one rule. Start on a node and measure the distance from the query to each of its neighbors. Move to the neighbor closest to the query, then repeat from there. Stop when none of the current node's neighbors is closer to the query than the current node itself. The node where you stop is the answer.

This is a greedy search, because each step chooses the neighbor that looks best right now. It never checks whether a step that looks worse now could lead to a better node later.

Press Advance one hop to run the rule one step at a time. The hollow rings mark the neighbors being measured, and the search moves to the closest one.

For this query, the search reaches the answer after 29 hops and 80 distance checks, instead of the 500 checks a full scan would use.

Step 3 / 6

The walk gets stuck, so keep more than one candidate

Greedy search has a failure case. Sometimes none of the current node's neighbors is closer to the query even though a better vector exists elsewhere in the graph. That current node is a local minimum, i.e. every neighbor is farther from the query, so a one-candidate search has nowhere better to move and stops with the wrong answer.

To get past that problem, keep the best few candidates found so far instead of only one. The number of candidates kept is the beam width, i.e. what the HNSW paper calls ef. When the current best candidate runs out of closer neighbors, another candidate can still lead the search into a better part of the graph.

The query below is placed where a beam width of 1 gets trapped. The search crosses most of the map, then stops on a vector about 10 times farther from the query than the true nearest. The dashed ring marks the true nearest. Raise the beam width and the search can reach it instead.

One query is not enough to show what a wider beam buys you, so the page also measures the same graph across the whole map. With a beam width of 1, this graph returns the true nearest 25 percent of the time and uses 29 distance checks on average. With a beam width of 8, it returns the true nearest 95 percent of the time and uses 62 checks on average.

A wider beam therefore costs more work, but it gives the search more ways to escape a local minimum.

Step 4 / 6

Short links move the search a short way, so add a few long ones

Now there is a different problem. Every link so far joins a vector to one of its four nearest vectors, so each hop moves only a short distance across the map. When the query is far from the entry point, the search needs many short hops to get there. The query in step 2 took 29 hops.

Now give every vector one extra link. Draw each extra link so that every doubling of distance gets roughly the same share, i.e. about as many links land between one and two units away as between two and four units away, and so on. These are the long links, and they create a small world. Work published in 2000 showed that this kind of distance rule makes greedy search efficient in a specific model, i.e. a two-dimensional lattice with local lattice connections and one directed long-range contact per node. The graph here is different because the vectors are scattered rather than placed on a lattice, and its links run both ways. So this figure borrows the same idea rather than applying that result directly.

Turn the long links on below. The search still keeps a single candidate, exactly as in step 2, but now one hop can cover much more distance.

For this query, the path falls from 29 hops to 4, and the work falls from 80 distance checks to 34.

Step 5 / 6

Put the long links on layers of their own

Putting long and short links in one graph helps, but every search step has to consider both kinds together. HNSW separates distance scales by placing vectors on different layers. Sparse upper layers provide longer links, while the dense bottom layer provides shorter ones.

When a vector is added to the index, it receives a top layer chosen at random. In this build, the draw is set so that roughly one in every M vectors reaches the next layer, where M also sets how densely the graph is linked. Each higher layer therefore contains only a fraction of the vectors below it. Basically each vector rolls a weighted die when it joins, and most of them stop at layer 0, roughly one vector in six also reaches layer 1, and roughly one in six of those reaches layer 2. With 500 vectors and M set to 6, layer 0 holds 500, layer 1 holds 89, layer 2 holds 20, and layer 3 holds 1.

M does two jobs in this build. First, it limits how many links a vector can keep, i.e. up to M links on the upper layers and up to 2M on layer 0. Second, it sets how quickly the layers thin out. The paper treats these as separate settings and suggests tying them together, which is the choice used here.

Thinner layers naturally create longer links. When a layer contains fewer vectors, those vectors are farther apart, so connections between nearby vectors on that layer span more distance. Layer 0 contains every vector, so its vectors are packed more closely and its links are shorter.

The search starts at the highest layer and moves toward the query using the links available there. When no neighbor on the current layer is closer, the search keeps its current position and drops to the next layer, which contains more vectors. It repeats that process until it reaches layer 0.

Each drop gives the search a denser graph in which to make a smaller correction. By the time the search reaches layer 0, it is usually already near the query. Layer 0 is where the beam width applies, i.e. the search keeps its best few candidates there and explores from them before deciding it can stop.

HNSW still does not guarantee the true nearest vector. The search only measures vectors it reaches, so it can stop on a close vector while a closer one remains unseen. That is why HNSW is an approximate nearest neighbor method. For an index that is already built, beam width is the main setting you control at search time. Raising it makes the search do more work and makes it more likely to return the true nearest vector. How often a search returns the true nearest is what people call its recall, and recall also depends on how the index was built, i.e. on M and on the choices made while inserting vectors.

With the same query and the same 500 vectors, the layered search now uses 45 distance checks.

Step 6 / 6

Set the controls yourself

You have now met each control. Points sets the number of vectors in the index. Beam width sets how many candidates the search keeps on layer 0. Links per vector is M. In this build, M caps a vector at M links on the upper layers and 2M on layer 0, and it also sets how quickly the layers thin out.

Start with the first experiment. It raises the index from 500 vectors to 1,500 while leaving the query and beam width unchanged. For this one query, the search moves from 45 distance checks to 43. That result shows why index size and search work do not rise one-for-one in this example.

Two simplifications matter here. First, the vectors have two dimensions so that you can watch the search move across a map, while real embeddings often have hundreds of dimensions. The 2D view is a teaching device rather than a scale model, so the hop counts and distance-check counts here should not be read as predictions for a real index. Second, this index stops at 1,500 vectors, while production indexes can hold millions.

The small end is where the layered search looks least impressive. At 100 vectors it still uses about 33 distance checks, i.e. about a third of the index. The work on any one layer is roughly bounded, while the number of layers grows slowly as the index grows. Over the 100-to-1,500 range in this playground, those effects make the total count change much less than a full scan would.
